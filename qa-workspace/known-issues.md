# Issues conocidos

> Problemas conocidos del ambiente/herramientas que NO son bugs de producto (flakiness conocida, limitaciones de datos, etc.).

- **Sin Xray/Zephyr en Jira**: no hay tracking nativo de test-execution vinculado a las historias. El adaptador `adapters/jira/` documenta esto — `listLinkedTests()` e `importTests()` son no-op a propósito (devuelven `[]`/conteo 0), no hay forma de "importar" casos de prueba a Jira en este proyecto todavía.
- **`core/lib/*.py`**: el template trae un pipeline Python de parseo de HUs (`read_hu.py`, etc.) pensado para proyectos con ese stack. Pendiente de decidir si se reemplaza por un equivalente `.mjs` o se elimina, ya que este proyecto es 100% Node/TypeScript.
- **Pool de usuarios `VETIFY_ADQUIRENTE` chico para el nivel de paralelismo local de `tests/projects/vetify-webapp/videocall.spec.ts`**: el archivo tiene 5 grupos `describe` (TS-02 a TS-05) que piden un usuario `numberOfPlans:1` con las mismas tags (`ACTIVE, WITH_PET, NO_EMPTY_PLAN`) — el pool solo tiene 4 usuarios así. Corriendo local con el default de workers (uno por core, 6+ en esta máquina) se observan fallos intermitentes por contención entre tests hermanos que comparten cuenta (uno cancela/agenda turnos mientras otro está a mitad de una aserción). **No reproducible con la config real de CI** (`playwright.config.ts`: `workers: 2` + `retries: 1` en CI) — confirmado corriendo `--workers=2 --retries=1` localmente: 0 failed. Si se agregan más specs que comparan turnos exactos (conteo, "próximo turno") contra este mismo pool, considerar agrandar el pool o mover esos describe a `mode: 'serial'` entre sí.
- **CORRECCIÓN 2026-08-05 (reemplaza la entrada anterior de "estado transitorio")**: la investigación inicial de por qué TS-02/03/04/05 fallaban consistentemente (con y sin Android corriendo en paralelo, con 1 o 2 workers, incluso tras matar procesos zombie de Playwright) apuntó en un primer momento a "contención externa" porque `apiClient.getUserPets()` devolvía `[]` a veces y `[pet]` otras para el mismo usuario en llamadas separadas por segundos. **La causa real, confirmada navegando manualmente (MCP) como 3 de los 4 usuarios pooled `VETIFY_ADQUIRENTE` tageados `ACTIVE, WITH_PET, NO_EMPTY_PLAN`** (`user_1782845996861`, `user_1782309368512`, `user_1782309546559`): las 3 cuentas muestran el gate **"Completá su credencial"** al iniciar una videollamada, y al intentar "Suscribir mascota" el sistema responde *"Para darle cobertura a una nueva mascota, primero elegí su plan en la web"* — es decir, **estas cuentas ya NO tienen un plan/póliza de mascota activo**, aunque el fixture `pooled-users.json` las sigue tageando `WITH_PET`. Las tags están desactualizadas respecto al estado real del backend QA (probablemente por expiración de póliza o un reset de datos del ambiente compartido en algún momento después de que se generaron estos fixtures). El flapping de `getUserPets()` entre `[]` y `[pet]` fue ambigüedad de timing sobre este mismo problema de fondo, no contención de otro proceso.
  - **Impacto**: TS-02, TS-03, TS-04, TS-05 de `videocall.spec.ts` están bloqueadas para CUALQUIER plataforma (Desktop o Android) hasta que se reemplacen o re-provisionen estas cuentas — no es un problema de mobile.
  - **Arreglo intentado y descartado**: completar la credencial vía UI ("Suscribir mascota") no es un fix rápido — redirige a un flujo de elegir plan + compra, el mismo proceso largo (registro + compra + espera de propagación de 5-20+ min, no determinística) ya documentado para usuarios `fresh`/IMP-004. No vale la pena repetirlo por cada cuenta pooled rota; más simple es re-provisionar cuentas `fresh` nuevas con el flujo estándar y agregarlas a `pooled-users.json`.
  - **Herramienta**: `scripts/maintenance/reset-pooled-user.mjs <email>|--all` — diagnostica pets/videollamadas agendadas de una cuenta pooled vía su `playwright/auth/<id>.json` cacheado y cancela turnos sueltos. Útil para turnos "colgados" (ej. el límite CA01/CA02 por acumulación de corridas), pero NO resuelve este problema de plan/póliza inexistente — eso requiere una cuenta nueva.
  - **Actualización tras retaggear (2026-08-05, más tarde el mismo día)**: se retaggearon las 3 cuentas rotas (`BROKEN_NO_PLAN`) dejando solo 2 sanas en el pool (`user_1782499435430`, `user_1782769587577`). Rerun con `--workers=2 --retries=1`: mejora real, de 9-10 failed / 1 passed a **5 failed / 3 passed**. Pero reruns posteriores (cache vieja + `workers=1`, sesión forzada fresca + `workers=2`, sesión fresca + `workers=1`) dieron todos **7 failed / 1 passed** — igual o peor, y esto descarta cualquier teoría de contención entre workers/sesiones: incluso una sola cuenta sana, con sesión 100% fresca y un solo worker (cero concurrencia posible), sigue fallando igual.
  - **CAUSA RAÍZ #1 (bug real, encontrado y arreglado)**: `VetifyWebappApiClient.cancelVideoCall()` (usado en el `beforeEach` de casi todos los describe de esta suite vía `cancelAllScheduledVideocalls()`) llamaba primero a `GET /api/services/pets/cancel_reasons` para armar el payload — ese endpoint devuelve **500 de forma consistente y reproducible** (confirmado en 2 cuentas distintas, siempre). Como `cancelAllScheduledVideocalls()` traga los errores (`.catch(() => {})`), la cancelación nunca funcionaba de verdad, y los turnos se fueron acumulando en cada corrida repetida del día hasta tocar el límite real de 2 por mascota (CA01/CA02), bloqueando "Agendar nueva videollamada" de forma determinística. **Confirmado que NO es un bug de producto**: el modal de cancelación real (`CancelVideocallModal.ts`, rediseño IMAS-3894) es "simple, sin selector de motivo" y llama directo a `PUT /cancel/{id}` sin pasar por `cancel_reasons` — ese endpoint es de una pantalla vieja que ya no existe en la UI actual. Fix aplicado: `cancelVideoCall()` ya no llama a `cancel_reasons`, llama directo al PUT (igual que la UI real). Ver también `scripts/maintenance/reset-pooled-user.mjs`, actualizado igual.
  - **CAUSA RAÍZ #2 (ambiental, NO arreglable desde este repo)**: incluso después del fix de arriba, se confirmó por separado —con **dos GET puros consecutivos, mismo token, sin ningún write de por medio, minutos aparte**— que `/api/services/pets/my-products` y `/api/services/assistance/local/programmed` devuelven resultados distintos para la MISMA cuenta (a veces con datos, a veces `[]`/`0`). Esto es inestabilidad de lectura real del backend del ambiente QA compartido (`vetify-qa.ikeapp.com`), no cache del framework ni de Playwright. **No es arreglable desde este repo** — hay que escalarlo a quien administre el ambiente/datos de QA compartido si se vuelve a observar tras el fix de la causa raíz #1.
  - **Importante para no repetir el error de esta sesión**: la UI manual (navegador real, un solo intento, sin agendar de más) funcionó siempre bien — tanto para el usuario del proyecto validando su cambio de responsive como para mí por MCP. La inestabilidad SOLO aparece en corridas automatizadas repetidas contra el mismo pool chico, y la causa principal (#1) ya tiene fix. Antes de reportar "falla igual en toda plataforma" como señal de bug de producto, verificar primero si `cancel_reasons`-like endpoints deprecados siguen devolviendo error y si las cuentas del pool no están ya en el límite por acumulación de corridas previas.
  - **Fix #1 verificado (2026-08-05, mismo día)**: tras el fix de `cancelVideoCall()` (usa `motivo_id: 1` fijo, sin depender de `cancel_reasons`) y limpiar el pool con `reset-pooled-user.mjs`, la corrida de `videocall.spec.ts` Desktop pasó de 7-10 failed a **6 passed / 1 flaky / 1 failed** en 3.2min (antes tardaba 12-14min). El único failed restante (TS-05 TC-01, botón "Cancelar" deshabilitado cuando debería estar habilitado con un turno agendado 5 días a futuro) se re-corrió aislado 3 veces seguidas (limpiando la cuenta entre cada corrida) y **pasó las 3 veces** — confirma que fue el mismo patrón de flakiness de lectura del backend (el endpoint `/pets/appointment/{id}` que alimenta esa pantalla también devuelve 500 de forma intermitente si se lo llama directo, aunque la sesión completa del browser real casi siempre lo resuelve bien). No se reporta como bug — no es reproducible, cae en la regla "no abrir bug si el fallo es de ambiente".
  - **CAUSA RAÍZ #3 (bug real de automatización, encontrado y arreglado)**: al fin correr Android limpio (con causa raíz #1 ya resuelta), apareció UN fallo genuinamente específico de mobile: `VideocallFormPage.confirmVideocallBtn` buscaba el botón por texto exacto `'Confirmar videollamada'` — ese texto solo aparece en Desktop. En mobile (viewport Android/Pixel 5), el mismo botón, en el mismo lugar, dice **"Continuar"** (mismo label genérico que usa el resto del wizard en esa plataforma). Confirmado por screenshot real de la corrida Android. Fix: `confirmVideocallBtn` ahora matchea `/^(Confirmar videollamada|Continuar)$/` — sin ambigüedad, la pantalla de revisión no tiene otro botón con esos textos.
  - **RESULTADO FINAL (2026-08-05)**, con las 3 causas raíz resueltas: `videocall.spec.ts` corre **100% limpio en ambas plataformas** — Desktop 10 passed/0 failed, Android 10 passed/0 failed (11 skipped en ambas, esperado: TS-01 sin usuario `NO_PET` disponible en el pool + placeholders de brecha/fuera-de-alcance documentados). La UI mobile funciona correctamente en todo el flujo de videollamada — la sospecha inicial del usuario del proyecto (que su cambio de responsive estaba bien y el problema era de la automatización) era correcta.
