# Estado actual del proyecto QA (arranque del agente)

> Fuente de arranque por sesión. Mantener actualizado: el agente lo lee primero para no depender solo del chat.

- **Proyecto**: `automation-main` — automatización QA E2E de los productos **Vetify** (B2C, institucional, webapp) y **OSDE** (Adquirente, Capitado) + **Flux Capitado**.
- **Stack**: Playwright + TypeScript. Reporte con **Allure** (`allurerc.js`, `allure-results/`, `npm run allure:report`). Sin capa API separada por ahora (todo vive bajo `tests/projects/`).
- **Gestor de tickets**: **Jira, sin Xray/Zephyr** → adaptador activo `adapters/jira/` (ver `adapters/jira/README.md`). El adaptador `none` quedó desactivado (`adapters/none/adapter.config.json` → `"active": false`).
- **Escrituras Jira**: guardrail formal en [`jira/update-rules.md`](../jira/update-rules.md) + [`jira/jira-workflow.md`](../jira/jira-workflow.md) — toda escritura real (`createDefect`) loguea en `jira/sync-log.ndjson`, verificado por `npm run validate:jira`. Smoke test de credenciales: `npm run jira:check`. Metadata (issue types/link types/transiciones): `npm run jira:metadata -- --issue=<KEY>`.
- **Idioma de tests**: **mixto, no elegir uno solo** — títulos de `test.describe()`/`test()` en español con prefijo `TC-XX`/`TS-XX` (contenido de negocio); identificadores de código (clases, métodos, variables, archivos) en **inglés**, según `documentation/development-standars.md`. No es la convención "todo español" del template genérico.
- **Ambiente activo**: variables de entorno gestionadas vía `src/config/environment.ts` + `src/config/sites.ts` (multi-sitio: cada producto/país tiene su propio `SiteId`). Confirmar contra ese archivo antes de asumir nombres de env vars nuevos.
- **Autenticación de test**: pool de usuarios reales vía `UserProvider` (`src/providers/user/`), no `storageState` global de un solo usuario admin. Ver skill `qa-spec-conventions`.
- **Estructura real de specs**: `test.describe('<Feature> Test Suite')` → `test.describe('TS-XX <categoría>')` → `test.describe()` anónimo con `test.use({ userRequest })` → `test('TC-XX - <Producto> - <escenario>', { tag: [...] }, async ({ container, page }) => {...})`. Ver skill `qa-spec-conventions`.
- **POMs**: jerarquía `BasePage` → `<Producto><App>BasePage` → `<Pantalla>Page`, en `src/pages/<producto>/<app>/`. Sin decorator `@step` (el step lo pone el spec con `step()` de `allure-js-commons`). Ver skill `qa-pom-authoring`.
- **Integraciones ya construidas** (sesiones previas): Jira (`scripts/jira/`, sin Xray) y Figma (`scripts/figma/`) — ambas funcionales, ver memoria persistente de usuario para detalles de uso.
- **GitLab (nuevo, 2026-08-21)**: `.env` ya trae `GITLAB_API_TOKEN` con acceso confirmado a `gitlab.com/grupo-ike-arg/webapp-mascotas/*` (reintegros-backend, backend-prestadores, webapp-proveedores-mascotas, y más que el usuario va agregando de a poco). **No hay cliente dedicado todavía** (a diferencia de Jira/Figma) — se usa `fetch` directo a `https://gitlab.com/api/v4/...` con header `PRIVATE-TOKEN`. Decisión tomada con el usuario: **leer vía API directa (archivos raw, diffs de MR, comentarios), no clonar el repo completo** salvo que haga falta ejecutarlo/debuggearlo de verdad — más liviano, no ensucia el working directory con repos que no son de este proyecto. Si el patrón de uso crece, considerar promoverlo a `scripts/gitlab/gitlab-client.mjs` siguiendo el mismo patrón que `scripts/jira/jira-client.mjs`.
- **Jira — comentarios con imágenes/videos (fix 2026-08-21)**: `extractText()` en `scripts/jira/jira-client.mjs` solo lee nodos de texto del ADF — **descarta en silencio** las imágenes/videos pegados en un comentario. Se agregó `extractMediaIds()` + `getComments()` (cuentan/listan referencias a media) y el comando CLI `media <KEY>` (lista adjuntos + qué comentario referencia cuáles). **Regla**: al analizar un ticket a fondo, correr `node scripts/jira/jira-client.mjs media <KEY>` además de `get` — un comentario con cuerpo casi vacío casi siempre significa que la evidencia real está en las imágenes/videos adjuntos, no en el texto.
- **Jira — links ocultos como hyperlink (hallazgo 2026-08-26, IMAS-3610)**: `extractText()` tampoco surface los `marks` tipo `link` (`href`) ni nodos `inlineCard`/`blockCard`/`embedCard` (`url`) — un texto como "ver el Figma acá" con un hyperlink aplicado se lee como texto plano, sin la URL. No hay todavía un comando CLI para esto (se resolvió con un script ad-hoc que camina el ADF buscando esos atributos, no comiteado). **Regla**: si la descripción/comentario menciona un archivo o "el link de..." sin URL visible en el texto extraído, sospechar hyperlink oculto antes de asumir que no existe. Pendiente de decidir si vale la pena promover esto a una función exportada de `jira-client.mjs` (ej. `extractLinks()`, mismo patrón que `extractMediaIds()`).
- **Jira — issues tipo "Tarea" guardan la descripción real en un campo custom, no en `description` (hallazgo 2026-08-27/28, IMAS-4408 e IMAS-4356)**: `getIssue()`/`fetchStory()` solo leen el campo estándar `description`. Confirmado en 2 tickets tipo **"Tarea"** de este proyecto: el campo estándar viene vacío, pero **`customfield_11620`** tiene la especificación completa (objetivo, criterios de aceptación, escenarios) tal como se ve en la UI de Jira. Un ticket tipo "Historia" (`IMAS-3610`) verificado que NO tiene este problema — su contenido real sí está en el campo estándar. **Costó una sesión entera de investigación sobre IMAS-4356 sin este contexto** (confound de segmento que el spec real ya resolvía sin ambigüedad) antes de descubrirse en un ticket distinto. **Regla dura**: ante cualquier issue con `description` estándar vacío, **chequear `customfield_11620` antes de concluir que la HU no tiene especificación** — especialmente si el tipo es "Tarea". Pendiente de decidir si conviene que `getIssue()`/`fetchStory()` revisen ambos campos automáticamente (no implementado todavía, requiere confirmar con el usuario si `customfield_11620` es estable/global o específico de la configuración de este proyecto Jira).
