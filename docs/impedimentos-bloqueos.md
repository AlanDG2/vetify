# Impedimentos y bloqueos QA

> Registro VIVO de lo que BLOQUEA tests HOY (no histórico). IDs `IMP-XXX` globales, nunca reusados. Referenciados desde los `test.skip` en el código (`// SKIP [IMP-XXX]: razón`). La skill `qa-troubleshooting` define el ciclo de vida.

## Dos tipos de impedimento — no todos se arreglan con código

Todo impedimento bloquea un test igual, pero la solución es de 2 tipos distintos:

- **🔧 Técnico/Ambiente**: hay un bug, falta infraestructura, o el ambiente está caído. Se arregla arreglando código/infra — no depende de que alguien decida algo, depende de que alguien lo arregle.
- **🧭 Contextualización**: el sistema ya hace lo que hace hoy, confirmado en vivo — lo que falta es que alguien con contexto de negocio/proceso responda una pregunta puntual (¿es intencional?, ¿existe un mecanismo?, ¿está en alcance?). No hay código que QA pueda escribir para resolverlo solo.

### Preguntas pendientes de contextualización — para llevar directo a quien corresponda

> Cada una tiene 4 partes: **Contexto** (qué es esto, para alguien que nunca escuchó hablar del tema), **Pregunta** (la que hay que hacer, tal cual), **A quién**, y **Qué cambia** según la respuesta. Si falta contexto para entenderla a la primera, está mal escrita — avisar para corregirla.

**IMP-009 — Canal para pedir builds Debug de la app mobile**
- **Contexto**: para poder automatizar contra un celular físico real (no el emulador), hace falta un build especial de la app llamado "Debug" — el build normal no permite inspeccionar lo que pasa adentro del WebView en un dispositivo real. Ya conseguimos uno, una sola vez, como pedido puntual.
- **Pregunta**: cada vez que la app se actualice, ¿cuál es el canal real para pedir un build Debug nuevo? ¿Hay algún proceso automático (un job de CI) que lo genere, o es siempre un pedido manual a una persona del equipo?
- **A quién**: equipo dev mobile (mismo contacto que dio el build actual).
- **Qué cambia**: si hay un canal reproducible, QA puede pedirlo solo cuando lo necesite. Si no, cada actualización de la app va a requerir volver a pedir este mismo favor de nuevo.

**IMP-015 — Proceso para dejar un plan "Inactivo/Dado de baja" en QA**
- **Contexto**: para probar qué le pasa a un cliente cuyo único plan quedó inactivo o dado de baja, necesitamos una cuenta de prueba en exactamente ese estado. Hoy la única forma de lograrlo es que Alexis Castellano entre directo a la base de datos y lo edite a mano — no existe ningún botón ni panel para hacerlo, ni para QA ni para nadie más.
- **Pregunta**: ¿existe o se puede armar algún proceso de autoservicio (un panel, un endpoint interno, lo que sea) para dejar un plan en ese estado en el ambiente de QA, sin depender de que una sola persona lo edite a mano cada vez?
- **A quién**: Alexis Castellano (a través de Paula Scalzo u Oscar Tello).
- **Qué cambia**: si existe o se crea, QA genera esta condición cuando la necesite. Si no, los 2 casos de prueba de IMAS-4408 van a depender para siempre de pedirle el mismo favor a Alexis cada vez que haga falta.

**IMP-018 — Simular una videollamada real y confirmar el envío de notificaciones**
- **Contexto**: cuando un cliente agenda una videollamada, hay 2 partes que hoy no podemos probar de forma automática: (1) que al entrar a la sala de espera, un profesional se conecte del otro lado y la consulta arranque de verdad — para esto haría falta simular a ese profesional; y (2) que al agendar/cancelar/reprogramar, le llegue realmente un email o notificación push al cliente — para esto haría falta alguna forma de confirmar que se mandó, más allá de lo que muestra la pantalla.
- **Pregunta**: ¿qué proveedor de videollamada usa el producto (Twilio Video, Agora, Daily.co, u otro)? ¿Ese proveedor ofrece algún modo de prueba (sandbox) con un participante automático que se conecte solo, simulando al profesional? Y para las notificaciones push en particular, ¿hay algún registro del lado del backend (un endpoint, un log) que confirme que se mandó la notificación, aunque no llegue físicamente al celular?
- **A quién**: equipo dev de Videollamada/Turnos.
- **Qué cambia**: si hay sandbox/bot y una forma de verificar el envío de notificaciones, esto se puede automatizar. Si no existe nada de eso, queda descartado para siempre — mismo criterio que ya se aplicó a otra parte de este mismo flujo (entrar a la sala dentro de los 5 minutos previos al turno), que se confirmó a mano y no se automatizó por no ser viable sin volverse un test lento.

**IMP-020 — Cómo se configura si un plan tiene o no el PDF de condicionado cargado**
- **Contexto**: uno de los estados que necesitamos poder probar es "el plan no tiene cargado el PDF de condicionado" (el documento que explica qué cubre el seguro). No encontramos ninguna cuenta real en ese estado, así que armamos un mock técnico como parche temporal para poder probarlo igual.
- **Pregunta**: ¿dónde o cómo se configura si un producto/plan tiene o no cargado ese PDF? ¿Existe un panel de administración del catálogo de productos, o se carga por otro medio que no conocemos?
- **A quién**: equipo de backend/catálogo.
- **Qué cambia**: con la respuesta, QA puede generar esa condición de datos reales cuando la necesite (para este caso, y para cualquier otro futuro parecido), en vez de depender siempre del mock como parche.

**IMP-022 — ¿Existe la "Encuesta CE" que asume el roadmap?**
- **Contexto**: el roadmap tiene un ítem que asume que existe una encuesta de satisfacción que aparece justo después de que un cliente termina de cargar la credencial de su mascota. Revisamos todo el código de la webapp buscando algo así, y lo único relacionado a encuestas que encontramos es Hotjar (una herramienta externa de analítica de terceros) — pero no hay ningún disparador propio de la app atado a "el cliente terminó de cargar la credencial".
- **Pregunta**: ¿existe realmente una encuesta configurada en Hotjar que se dispare específicamente al completar la credencial? Si existe, ¿bajo qué condición se dispara (por URL, por tiempo en la página, por algún evento)?
- **A quién**: Producto / Marketing (quien administra el panel de Hotjar).
- **Qué cambia**: si existe, queda fuera del alcance de esta automatización — Hotjar no es algo que se pueda verificar de forma confiable con Playwright, se cubriría manual o desde el propio panel de Hotjar. Si no existe, se saca directamente del roadmap.

**IMP-024 — 3 funcionalidades del roadmap que no encontramos en la app real**
- **Contexto**: al explorar la app real buscando 3 ítems del roadmap, no los encontramos como se describen: (1) un selector para "elegir qué mascota está activa" en toda la sesión — hoy cada pantalla simplemente lista todas las mascotas del cliente, no existe tal selector fuera del flujo de Videollamada; (2) una pantalla de "detalle de una veterinaria" con ficha/información del prestador — hoy "Buscar veterinaria" es solo un mapa de Google centrado en una dirección, sin lista de resultados ni ficha de ningún prestador; (3) una función llamada "Atención de Red" — revisamos los 15 ítems reales del menú lateral y ninguno se llama así, ni parece ser algo distinto de Emergencias/Asistencia/Historial, que ya están cubiertos con otro nombre.
- **Pregunta**: para cada uno de los 3 — ¿está planeado construir esto en algún momento, o el roadmap se refería en realidad a algo que ya existe con otro nombre?
- **A quién**: Producto.
- **Qué cambia**: con cualquier respuesta (construir a futuro, o confirmar que ya está cubierto y sacarlo del roadmap), el ítem deja de figurar como "0%, pendiente" para siempre sin ningún motivo real detrás.

**IMP-026 — Mecanismo real para cambiar el DNI de una cuenta**
- **Contexto**: confirmamos en vivo que dentro de la app no existe ningún campo para cambiar el DNI de una cuenta — la única forma real es llamar al 0800 y que un agente de soporte lo cambie del otro lado. Para poder probar "qué pasa si intento comprar de nuevo con el DNI viejo/nuevo después de un cambio así", necesitaríamos una cuenta que ya haya pasado por ese cambio — y hoy no hay forma de generar esa condición nosotros mismos.
- **Pregunta**: el agente de soporte que hace ese cambio, ¿usa algún panel o sistema interno al que QA podría pedir acceso? ¿O es 100% manual, sin ninguna herramienta detrás que se pueda usar?
- **A quién**: equipo que atiende el 0800 de soporte.
- **Qué cambia**: si hay un panel, QA pide acceso y genera esa condición cuando la necesite (mismo patrón ya resuelto antes para otros casos parecidos, ver IMP-013/IMP-015). Si no hay nada, esos 2 casos de prueba quedan permanentemente imposibles de automatizar — no por falta de esfuerzo, sino porque no existe ningún camino repetible para llegar a esa condición.

**IMP-001 (para cuando se agoten los tokens de cupón Capitado)**
- **Contexto**: para dar de alta una cuenta nueva en los productos Capitado (OSDE/Flux) hace falta un código de "cupón" de un lote que nos dieron una sola vez (20 códigos, el 2026-09-03). Ya usamos varios; el día que se terminen, no vamos a poder seguir probando altas nuevas de esos productos.
- **Pregunta**: cuando se agoten, ¿cuál es el proceso real para conseguir/generar un cupón nuevo? ¿Hay un panel, un endpoint interno, o hay que pedirle un lote nuevo a la misma persona cada vez?
- **A quién**: el mismo contacto que dio los 20 tokens originales.
- **Qué cambia**: si hay un mecanismo propio, se automatiza la generación on-demand (que es lo que se había pedido originalmente en IMAS-3970). Si no, al menos queda documentado el proceso real, para no tener que volver a averiguarlo de cero la próxima vez.

**IMP-005 — Cómo dar de alta un usuario de prueba en el sistema de identidad de Iké**
- **Contexto**: para probar el control de acceso entre la webapp de Vetify y la de Iké (qué pasa según si un cliente tiene plan de uno, del otro, de ambos, o de ninguno), necesitamos cuentas de prueba que existan en el sistema de identidad propio de Iké — un sistema separado del de Vetify, sin autoservicio. Hoy no tenemos ninguna cuenta así.
- **Pregunta**: ¿cómo se da de alta un usuario en el sistema de identidad de Iké? ¿Qué panel se usa, qué datos hace falta cargar, quién tiene permiso para hacerlo?
- **A quién**: equipo/responsable del sistema de identidad de Iké (Auth0 `ike-webapp-staging.us.auth0.com`).
- **Qué cambia**: con al menos 1 cuenta solo-Iké y 1 cuenta con ambos planes, se destraban 5 casos de prueba que hoy están completamente bloqueados.

**Nota sobre IMP-025**: es distinto de los de arriba — no es una pregunta de negocio, es una decisión de arquitectura interna del propio framework de automatización (pool Fresh sin cacheo vs. volver a Pooled). Se resuelve entre QA y quien mantenga `UserProvider`/`UserFactory`, no con una persona externa.

## IMP-009 — detalle (WebView sin remote debugging en el build entregado — acotado a celular físico)

**Síntoma original**: contra el celular físico (Motorola Edge 60), `browser.getContexts()` devuelve siempre `['NATIVE_APP']`, nunca aparece un `WEBVIEW_*`, sin importar cuánto se espere (probado con polling de 20s tras el launch).

**Causa raíz confirmada** (no es timing, no es de red, no es config de Appium): `MainActivity.java` (repo `ike-webapp-mobile`) tiene:
```java
if (BuildConfig.DEBUG) {
    WebView.setWebContentsDebuggingEnabled(true);
}
```
`WebView.setWebContentsDebuggingEnabled()` es el interruptor que expone el WebView vía Chrome DevTools Protocol — es lo que Appium/`chromedriver` necesitan para detectar y adjuntar un contexto `WEBVIEW_*`. Como este apk es un build **release** (`android:debuggable=false`), `BuildConfig.DEBUG` es `false`, así que esa línea nunca se ejecuta en el celular físico. Confirmado empíricamente: `adb shell dumpsys package vetify.cliente.dev` → `flags=0x0` (sin `DEBUGGABLE`).

**CORRECCIÓN el mismo día — el bloqueo NO es total, es específico de celular físico**: al armar el emulador (AVD `Pixel_6_QA`, Android 14 `google_apis` x86_64) y correr el mismo apk ahí, el contexto `WEBVIEW_vetify.cliente.dev` **apareció inmediatamente**, sin ningún cambio de código ni de apk. Investigado por qué: `adb shell getprop ro.debuggable` da `1` en el emulador y `0` en el celular físico. Las imágenes de sistema `google_apis` (no `google_apis_playstore`) del emulador son builds **"userdebug"** de Android — cuando el SO entero es debuggable, el WebView se puede inspeccionar vía Chrome DevTools **sin importar el flag `BuildConfig.DEBUG` de la app individual**. Un celular real de fábrica corre un build **"user"** (`ro.debuggable=0`), que sí respeta estrictamente el opt-in de cada app. Es decir: la gate de `MainActivity.java` solo importa en hardware real, no en el emulador.

**Ajuste adicional necesario para interactuar (no solo detectar) el WEBVIEW**: al hacer `switchContext()`, Appium tiró `No Chromedriver found that can automate Chrome '113.0.5672'` — hace falta que Appium descargue el chromedriver que matchea la versión de Chrome/System WebView del emulador. **CORRECCIÓN el mismo día, más tarde (armando la exploración de `Emergencias`/side menu)**: la mitigación de reiniciar el emulador **NO es 100% confiable** — 4 intentos seguidos de un mismo test nuevo fallaron con el mismo síntoma, incluyendo uno corrido inmediatamente después de un reinicio en limpio (mismo procedimiento que había funcionado un rato antes). No hay todavía un patrón claro de cuándo el restart ayuda y cuándo no — tratar el restart como "vale la pena probarlo, no como solución garantizada". De paso, se reconfirmó el riesgo del pool: los 10 usuarios `ACTIVE` de `VETIFY_ADQUIRENTE` quedaron reservados por completo otra vez tras esta racha de fallos — liberados manualmente. **Recomendación honesta en este punto**: no seguir insistiendo indefinidamente con reintentos/restarts cuando algo falla repetido — cortar, avisar, y decidir con el usuario del proyecto si vale la pena seguir invirtiendo tiempo en el emulador o esperar el build Debug para celular físico.

## IMP-011 — detalle (subir archivo a un `<input type="file">` del WebView crashea la app entera)

**Contexto**: portando `TS-02 Cargar credencial - Validación de Pasos` (Playwright) a mobile (`credential-wizard.spec.ts`, TS-08), el paso 5 del wizard (foto de la mascota) requiere setear un `<input type="file">` real. Playwright resuelve esto con `setInputFiles()`, que no existe en WebdriverIO.

**3 intentos, en orden**:
1. `browser.uploadFile(localPath)` — falla con `The uploadFile command is not available in undefined`. Depende del comando W3C estándar `file` (arma un zip y lo sube a un servidor Selenium/chromedriver standalone) — Appium no expone ese comando en la sesión.
2. `browser.pushFile(devicePath, base64Data)` + `.setValue(devicePath)` — el `pushFile` (extensión propia de Appium, `POST .../appium/device/push_file`) sí funciona y copia el archivo al dispositivo, pero el `.setValue()` posterior falla con `path is not absolute: /sdcard/Download/...`. Chromedriver (que es quien realmente maneja el `<input>` dentro del WebView, no UiAutomator2) rechaza la ruta porque espera una ruta absoluta del **host** (Windows) — tiene su propio mecanismo para transferir el archivo del host al proceso del browser a través del túnel de debugging, no usa rutas del dispositivo.
3. `.setValue(localPath)` directo (ruta absoluta del host, igual que Playwright) — el comando en sí se ejecuta sin error (`RESULT null`), pero **~100-300ms después la app entera crashea**.

**Causa raíz confirmada en logcat** (no es timing ni el emulador — `adb logcat -d` capturado inmediatamente después de la corrida):
```
chromium: [ERROR:bad_message.cc(29)] Terminating renderer for bad IPC message, reason 2
ActivityManager: Killing ...com.google.android.webview:sandboxed_process0... isolated not needed
chromium: [ERROR:aw_browser_terminator.cc(156)] Renderer process (24444) crash detected (code -1).
chromium: [ERROR:aw_browser_terminator.cc(112)] Render process (24444) kill (OOM or update) wasn't handed by all associated webviews, killing application.
ActivityManager: Process vetify.cliente.dev (pid 24413) has died: fg TOP
```
El mecanismo de subida remota de chromedriver (inyecta el archivo del host directo en el proceso del navegador vía IPC interno) le manda al Chromium embebido en esta WebView (versión 113, vieja) un mensaje que el validador de IPC del browser process considera malformado/no confiable (`bad_message.cc` es el guardrail de seguridad de Chromium contra procesos renderer comprometidos) — lo mata. Como la app no maneja ese renderer-crash de forma aislada (`kill wasn't handed by all associated webviews`), Android termina matando el proceso completo de la app, no solo el WebView.

**Reproducido 2/2, mismo punto exacto ambas veces** (~34.66s → crash a los 34.9s aprox., en ambas corridas) — no es un flake tipo IMP-010, es determinístico.

**No es un bug de producto**: un usuario real tocando el botón de subir foto dispara el selector nativo de archivos de Android (interceptado por `onShowFileChooser` en `MainActivity.java`), un camino completamente distinto al que usa chromedriver para inyectar el archivo de forma remota. Este crash es 100% un artefacto de cómo la automatización fuerza el valor del input, no algo que un usuario real pueda gatillar.

**Decisión**: `credential-wizard.spec.ts` TC-01 verifica que el wizard llega al paso 5 (título correcto, input y preview presentes en el DOM) pero **no llama a `uploadPetPhoto()`** — el método queda en `AddPetFormPage.ts` (documentado como roto) por si una versión futura del WebView de la app (Chromium más nuevo) deja de rechazar el IPC, pero no se usa en ningún spec activo.

**Alcance más amplio**: cualquier otro flujo con subida de archivo dentro de la app (foto de perfil/avatar, adjuntos de videollamada si se llegan a portar) va a pegar contra el mismo bloqueo de fondo — no vale la pena reintentar variantes del mismo mecanismo (ya se probaron 3) sin antes confirmar si una versión más nueva de Chromium/WebView del sistema cambia algo.

**RESUELTO 2026-08-12 — workaround real encontrado, no un cambio de Chromium**: en vez de forzar el input directo, se automatizó lo que un usuario real hace: tocar el `<label for="pet-photo-file-input">` visible (no el `<input>` oculto). Confirmado en vivo con `browser.getCurrentPackage()`: el tap dispara `onShowFileChooser()` de Android y abre el **selector nativo de fotos moderno** (`com.google.android.providers.media.module`, actividad "Photo Picker") — un contexto `NATIVE_APP` normal, automatizable con UiAutomator2 sin tocar chromedriver en ningún momento. Cada miniatura del picker es un elemento clickeable con `content-desc="Photo taken on <fecha>"` (confirmado con `uiautomator dump`, no son los `ImageView` sueltos de la toolbar). Al tocar una miniatura, la app vuelve a `vetify.cliente.dev` sin crashear y el `<img>` de preview del WebView queda con un `blob:` URL real — la subida funciona de punta a punta.

Implementado como `BasePage.selectPhotoViaNativePicker(triggerLabelSelector)` (`mobile/pages/BasePage.ts`) — reutilizable por cualquier pantalla con un patrón `<label for="...">` + `<input type="file">` oculto (foto de mascota, y probablemente foto de perfil/avatar, aunque cada pantalla necesita su propia verificación en vivo antes de asumirlo). **Precondición importante**: el picker moderno solo muestra fotos ya indexadas por MediaStore — hay que empujarlas antes con `adb push` + un broadcast `MEDIA_SCANNER_SCAN_FILE` (ver el hook `before()` de `credential-wizard.spec.ts` para el patrón exacto). `AddPetFormPage.uploadPetFilePhoto()` ya usa este workaround — verificado 2/2 contra el emulador, sube la foto real y llega al final del paso 5 (preview visible, botón "Continuar" habilitado) sin crashear.

**No confundir con las 3 rutas descartadas arriba** (siguen bloqueadas, no cambiaron): esto NO es una forma de setear el `<input>` directo — es evitar el input directo por completo, automatizando el flujo de UI real de extremo a extremo (WebView → tap → picker nativo → tap → WebView).

**Reabrir si**: el workaround deja de funcionar (ej. Android cambia el picker nativo, o la app deja de implementar `onShowFileChooser`) — en ese caso sí valdría la pena retomar la búsqueda de una forma de setear el input directo (los 3 caminos ya descartados arriba, o alguno nuevo).

**Extendido 2026-08-12, mismo día — foto de perfil confirmada, con un trigger distinto al de mascota**: el `<input type="file">` del avatar de perfil (`profile.spec.ts` TC-03) NO tiene `<label for="...">` asociado, a diferencia del paso de foto de mascota — el trigger real confirmado en vivo es el propio `div[data-scope="avatar"][data-part="root"]` (clickear el contenedor directo del input no dispara nada). `BasePage.selectFileViaNativePicker()` (renombrado desde `selectPhotoViaNativePicker` al generalizarse, ver más abajo) no necesitó cambios en su lógica — ya recibía el selector como parámetro genérico. Verificado 2/2 en aislamiento.

**Extendido 2026-08-12, mismo día — adjuntos de videollamada confirmados: un SEGUNDO picker nativo distinto, y un trigger que exige tap real (no JS)**: `videocall.spec.ts` TS-03 TC-02 ("Adjuntos - Carga y borrado de archivo válido"). Dos hallazgos nuevos acá:
1. **El trigger no responde a NINGÚN evento sintético.** El dropzone (`div[aria-disabled="false"]`, sin `<label>` ni `data-scope`) no reacciona a un click JS simple, ni a una secuencia completa `pointerdown`+`mousedown`+`pointerup`+`mouseup`+`click` disparada por `dispatchEvent()` — todo confirmado en vivo, sin efecto. Lo único que funciona es un tap NATIVO real (`.click()` de WebdriverIO, no `browser.execute(el => el.click())`) — aunque ese tap nativo casi siempre choca primero con "element click intercepted" (mismo problema de viewport angosto de siempre) y depende del fallback automático de WebdriverIO tras agotar sus 3 reintentos para terminar disparando el picker.
2. **Se abre un picker nativo DISTINTO**: como el input acepta `image/*,video/*,application/pdf` (no solo imagen, a diferencia de mascota/avatar), Android no ofrece el Photo Picker moderno — abre el selector de archivos completo / Storage Access Framework (`com.google.android.documentsui`, actividad `PickActivity`). Su UI es otra: tarjetas de archivo clickeables con `resource-id="com.google.android.documentsui:id/item_root"` (confirmado con `uiautomator dump`), no `content-desc="Photo taken on..."`.

`BasePage.selectPhotoViaNativePicker()` se generalizó y renombró a **`selectFileViaNativePicker()`**: prueba click JS primero (funciona en mascota/avatar), y si el paquete no cambió, cae a `.click()` nativo (necesario acá); después detecta cuál picker abrió (`documentsui` vs Photo Picker) y usa el selector correspondiente. Un locator inicial del nombre de archivo adjuntado (`//p[contains(., ".jpg") or ...]`) resultó ser un falso positivo — matcheaba también el texto estático fijo "Formatos permitidos: .png, .jpg o .pdf" del dropzone vacío, por lo que el chequeo de "se borró" (`waitForExist({reverse:true})`) nunca se cumplía. Corregido anclando al botón de borrar real (`button[data-cy="filePreviewDelete"]`, único cuando hay un archivo adjuntado) y subiendo al `<p>` hermano. Verificado 2/2 (subida + borrado, ciclo completo).

Con esto, **IMP-011 queda resuelto en las 3 pantallas de subida de archivo del alcance actual**: foto de mascota, avatar de perfil, adjuntos de videollamada.
