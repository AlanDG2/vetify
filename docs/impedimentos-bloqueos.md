## IMP-005 — detalle (IMAS-3742, WebApp de Iké sin infraestructura de pruebas)

**Contexto del bug**: usuarios con únicamente planes de Vetify pueden autenticarse e ingresar a la WebApp de Iké (incidente en producción, `IMAS-3742`, "In Validation"). El dev pidió 4 pruebas: usuario Vetify-only → solo Vetify; usuario Iké-only → solo Iké; usuario con ambos → ambas; usuario sin ningún plan → ninguna.

**Por qué está bloqueado para automatización** (investigado exhaustivamente 2026-08-05 antes de abrir este impedimento — no es una suposición):
- `src/config/sites.ts` / `environment.ts` / `.env` / `.env.example` solo definen `VETIFY_WEBAPP_BASE_URL=https://vetify-qa.ikeapp.com`. No hay `SiteId`, URL, ni entrada de sitio para una WebApp de Iké separada.
- No hay POMs (`src/pages/`) para ninguna pantalla de la WebApp de Iké.
- Confirmado en la transcripción `transcripciones/Process Training - Mascotas-20260731_113836-*.vtt` (~min 21-22 y ~min 40) que "Iké Mascotas" es un sistema **legacy separado** de Vetify, y que provisionar un usuario de prueba de Iké en QA **no es autoservicio** como en Vetify ("no tengo usuario de Iké", "en Iké no es tan fácil" — Javier Caballero, dev del equipo).
- El catálogo manual de casos (`documentation/Casos de Prueba.xlsx`, hoja "Registración y Adquisición") ya reservaba 4 filas placeholder (`CP-04.01`-`CP-04.04`, categoría "04 Iniciar sesión") para esta combinatoria, vacías desde su creación — nunca se completaron ni automatizaron.
- Se buscó la URL de QA de Iké en todo el repo (código, `.env`, docs, Figma exports, transcripciones) sin encontrarla — confirmado con el usuario del proyecto que tampoco la tiene a mano.

**Qué se hizo mientras tanto** (2026-08-05): se completaron los 6 casos de prueba manuales en `documentation/Casos de Prueba.xlsx` (`CP-04.01` a `CP-04.06`) con Precondiciones/Pasos/Resultado Esperado completos. **Corrección 2026-08-06**: al buscar esos casos para retomarlos, no se encontraron en ningún xlsx del repo (ni el actual `documentation/Casos de Prueba (1).xlsx` ni su backup) — el archivo referenciado el 2026-08-05 no es el mismo que existe hoy, o esos casos nunca se guardaron. Se redefinieron los casos de cero a partir de los criterios de aceptación reales de `IMAS-3742` en Jira (ver más abajo), en vez de asumir el contenido perdido.

**Destrabado parcialmente 2026-08-06**: el usuario del proyecto pasó la URL de QA de la WebApp de Iké (`https://ikeargentina-qa.ikeapp.com`). Se agregó `SiteId.IKE_WEBAPP` (`environment.ts`, `sites.ts`, `.env`/`.env.example`), un POM mínimo (`src/pages/ike/webapp/{BasePage,LoginPage}.ts`, confirmado vía MCP contra QA real — mismo diseño que el login de Vetify webapp pero sin `data-cy`, se usan locators por rol) y se registró en el `container` de `tests/framework/base-test.ts`. Nuevo spec: `tests/projects/ike-webapp/access-control.spec.ts`.

- **TC-01 (CA01/CA04 — plan exclusivo de Vetify) ✅ automatizado y pasando**: se reserva un usuario real del pool `VETIFY_ADQUIRENTE` (`ACTIVE, WITH_PET` — plan exclusivo de Vetify) vía `UserProvider.getUser()` (solo se necesitan las credenciales, no un login completo a Vetify webapp) y se intenta loguear directo en el login de Iké. Resultado: rechazado con el mensaje genérico "La contraseña y/o correo electrónico no es válido.", sin avanzar de `/auth/login`. **Ambigüedad no resuelta**: no se pudo determinar con certeza si el rechazo se debe a que el fix (`IMAS-3744`) ya bloquea el acceso en la autenticación, o a que esta cuenta de automatización (creada solo para Vetify) nunca tuvo un registro propio en el sistema de identidad de Iké — el resultado observable (sin acceso) coincide con CA01/CA04 en cualquiera de los dos casos, pero para cerrar la HU con confianza real hace falta un usuario Iké-only confirmado que SÍ pueda loguear, para descartar la segunda hipótesis.
- **TC-02 (CA02, plan Iké) / TC-03 (CA03, ambos planes) / TC-04 (sin ningún plan) / TC-05 (CA05, regresión) — siguen bloqueados**: sigue sin resolverse la parte (b) del impedimento original (usuarios de prueba con plan de Iké). Documentados como `test.skip` con motivo explícito en el spec.

**Regla de mobile (2026-08-05, `feedback_always_validate_desktop_and_mobile`)**: el sitio `Ike WebApp` NO tiene proyecto mobile habilitado en `playwright.config.ts` todavía (el mobile solo está habilitado para `Vetify WebApp`) — TC-01 solo se validó en Desktop.
