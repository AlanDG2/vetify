## 2026-08-04 - Fix: `createDefect()`/`checkClosable()` no reconocían el issuetype real de bug ("Error", no "Bug")
Decisión: `createDefect()` (`adapters/jira/client.mjs`) creaba el defect vía `createChildTask()` — un issue tipo **Subtarea**, forzado por esa función genérica (también usada por el comando CLI `jira create <PARENT> <summary>`, que sí debe seguir creando Subtareas). `checkClosable()` buscaba `issuetype.name === 'bug'` (string fijo en inglés). Ninguno de los dos matcheaba con el issuetype real de este proyecto Jira (IMAS): **"Error"** (confirmado vía `npm run jira:metadata` — no existe un tipo llamado "Bug" en absoluto). Resultado: cualquier defect creado con `createDefect()` quedaba invisible para el criterio 6 del DoD — `checkClosable()` reportaría `closable: true` aunque el bug siguiera abierto. Se agregó `createIssue()` (`scripts/jira/jira-client.mjs`, issue de proyecto sin `parent`) y se cambió `createDefect()` para usarlo con `issuetype: "Error"` + `linkIssues(parentKey, 'Blocks', defectKey)` en vez de `createChildTask()`. `checkClosable()` ahora matchea contra un set `{bug, error}` (case-insensitive) en vez de un string fijo.
Razón: descubierto al preparar el primer `createDefect()` real de la sesión (BUG-001, IMAS-3899) — encontrado ANTES de crear el primer defect real, no después de que el gate ya hubiera fallado en producción. Los cierres de HU de esta misma sesión (IMAS-3174, IMAS-3889) no se ven afectados: `checkClosable()` no encontró ningún `issuelink` en ninguno de los dos casos (el gate roto habría dado el mismo resultado "closable" que el gate arreglado), pero el mecanismo en sí estaba roto de cara a cualquier defect futuro.
Reabrir si: el proyecto Jira agrega/renombra el issuetype de bug otra vez, o si se detecta que "Error" no admite `linkIssues()` con tipo "Blocks" en algún subproyecto.

## 2026-08-04 - Fix #2 (mismo día): `createDefect()` no completaba el campo real "Descripción del error" del issuetype "Error"
Decisión: al crear el primer defect real (IMAS-4102, BUG-001) se detectó que el issuetype "Error" de este proyecto Jira tiene un **campo custom propio** (`customfield_11621`, "Descripción del error") con una plantilla fija de 6 paneles (Breve descripción / Pasos para reproducir / Resultado actual / Resultado esperado / Ambiente y Entorno / Evidencia) — **separado** del campo `description` genérico que sí completaba `createDefect()`. Sin tocar ese campo, Jira lo deja con su placeholder por defecto (texto entre corchetes tipo "[Describí de forma concisa el problema encontrado]"), visualmente indistinguible de "el bug está vacío" para cualquiera que abra el issue. Se agregó `updateIssueFields()` (`scripts/jira/jira-client.mjs`, PUT genérico) y `buildDescripcionDelError()`/`buildDescripcionDelErrorPanel()` en el adaptador para construir los 6 paneles en ADF real. `createDefect(bug)` ahora acepta campos estructurados opcionales (`steps`, `actualResult`, `expectedResult`, `environment`, `evidence`, `briefDescription`) y completa el campo real en la misma llamada. IMAS-4102 se corrigió a mano con un script puntual (`.tmp-fix-imas4102.mjs`, borrado tras usarlo) antes de este fix.
Razón: el campo `customfield_11621` es específico del screen scheme de "Error" en Jira Cloud — no hay forma de descubrirlo por API salvo leyendo `getIssue(key).fields` de un issue ya creado (no existe endpoint de "campos por issuetype" fácil desde este cliente). Se documenta acá el ID exacto para que no haya que re-descubrirlo.
Reabrir si: Jira reconfigura el screen scheme de "Error" (el ID de `customfield_11621` cambiaría) — verificar con `getIssue()` sobre un Error nuevo si `createDefect()` empieza a fallar silenciosamente en este campo otra vez.
